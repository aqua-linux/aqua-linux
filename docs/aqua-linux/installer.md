# Aqua Linux Installer

Milestone 9 implements the Aqua Linux graphical installer as a first-party Wayland client backed by the `aqua-installer` Rust crate. Its behavior remains complete; its visual convergence target is now the shared `ui-contract.md` and `interface-style.md` system.

## State Model

The initial state model is implemented without disk access or graphical rendering. Its ordered stages are:

1. Welcome
2. Language
3. Keyboard
4. Partitions
5. Time Zone
6. User Information
7. Summary
8. Installation
9. Completed

Forward navigation is blocked until the current stage has a valid selection. Installation and completion are terminal navigation states; the UI cannot return to editable steps once execution begins.

## Graphical Window Contract

- `InstallerWindowLayout` defines the responsive installer window, title bar, step rail, content region, footer, language control, cancel/back/forward controls, and progress track using the shared `aqua-scene` viewport and rectangle types.
- Layout checks cover 800x600, the 1280x800 QEMU target, and 1536x1024 reference composition. Every region remains inside the viewport; the title/content/rail/footer and footer controls do not overlap.
- All nine canonical steps expose their final Turkish labels. The state model supplies step-specific focus orders for content, language, cancel, back, forward, progress, and finish targets.
- Tab, Shift+Tab, Left, Right, Home, End, Enter, and Escape produce controller actions without bypassing the existing installer validation or destructive confirmation gates. Installation removes cancel/back navigation and exposes only the live progress status; completion exposes only the finish action.
- Footer pointer hit-testing uses the same responsive `InstallerWindowLayout` rectangles and emits the same `InstallerUiAction` variants as keyboard activation. Language, Cancel, Back, Forward/Install, and Restart are clickable only while visible for the current step; hidden Back, Cancel, and Forward controls reject hits.
- Choice, disk, and user-field rows now use geometry owned by `InstallerWindowLayout` for both raster drawing and pointer hit-testing. Choice clicks apply only bounded catalog values; blocked disks reject hits, eligible disk clicks change selection without applying `InstallerModel::target`, and user clicks change the active field without creating a profile. Target and profile application still require explicit Step Content activation.
- The packaged readiness probe validates the 1280x800 geometry, keyboard contract, bounded catalogs, password-content-free user state, and target-bound Summary contract while reporting `installer_ui_rendered=false` because it stays in recovery. The separate QEMU Wayland acceptance path validates real presentation and keyboard input through User Information.

## Welcome Raster

- `aqua-renderer` consumes the installer model, synchronized UI state, shared window layout, optional live progress event, and a validated RGBA Aqua logo source.
- The first 1280x800 software raster draws the current legacy bright window, title bar, controls, nine-step Turkish rail, Welcome content, feature row, footer controls, keyboard focus outline, and the current `aqua-symbol-primary.png` asset. Its behavior is retained while presentation is restyled.
- The renderer rejects unsupported viewports, malformed logo buffers, and stale UI state whose step differs from the domain model. Its probe requires valid layout, all nine steps, the real logo layer, at least 40 primitives, and a non-zero checksum.
- PNG export is deterministic and display-independent. `scripts/check-installer-render.sh` regenerates `build/installer-welcome.png`, validates its 1280x800 RGBA header, probe fields, checksum shape, and non-trivial size.
- RGBA image composition now multiplies layer opacity by source alpha. Transparent logo pixels preserve window content instead of producing an opaque black rectangle.
- This host raster is the same renderer output now consumed by the packaged Wayland installer client. The recovery-only Buildroot readiness probe correctly continues to report `installer_ui_rendered=false` because that probe never starts graphics.

## Packaged Wayland Surface

- `/usr/bin/aqua-installer` is packaged as the `aqua.installer` first-party client and connects only to the Aqua compositor's `wl_shm` plus `xdg_toplevel` protocol path.
- Its initial 1280x800 buffer is generated by the same `aqua-renderer` installer function used by deterministic host checks. The client loads `/usr/share/aqua/brand/aqua-symbol-primary.png`; missing, malformed, or unsupported logo data fails closed before a surface becomes active.
- The binary remains manual with `autostart=false` and live transaction execution disabled by default. The QEMU presentation test may set `AQUA_INSTALLER_PROGRESS_PRESENTATION_REHEARSAL=true`; this constructs and rehearses the canonical transaction graph through `NonExecutingInstallTransactionRunner`, requires `executed=false`, and never dispatches a process or filesystem write.
- The recovery readiness probe deliberately remains headless and reports `installer_ui_rendered=false`; it validates contracts without opening a compositor session.
- `scripts/check-installer-wayland-qemu.sh` boots the Buildroot image with a disposable second disk, starts the persistent-until-verified `installer-welcome` scenario, validates the packaged client and serial lifecycle, and captures Welcome, Keyboard, Partitions, Time Zone, Summary, Installation, and Completed frames from the QEMU monitor.
- The same acceptance starts a real `virtio-mouse`, clicks the Welcome Forward control, waits for its repaint, clicks a Language row, and then resumes keyboard navigation. The compositor maps `aqua.installer` input at the same `(0,0)` origin as its full-output presentation, so visible footer and content rectangles are physically reachable.
- Installer presentation is a dedicated full-output layer: its 1280x800 buffer maps one-to-one to the QEMU output and desktop top panel, dock, icons, overview, session menu, and notifications are excluded from the frame.
- The QEMU navigation acceptance forwards 108 press/release events through libinput and Aqua Seat. The client records 34 rerenders while applying `tr_TR.UTF-8`, `trq`, `/dev/vdb`, `Europe/Istanbul`, username `aqua`, display name `user`, password-configured status, and exact `ERASE /dev/vdb` confirmation. Printable characters are accepted only in bounded form fields; the password row stores status only, and the serial test rejects any `password=` content.
- After confirmation, the acceptance-only presentation rehearsal advances the graph at completed-step counts 8, 13, and 19, then emits the canonical completed event at 20/20. The renderer displays the active graph phase, completed/total steps, and percentage before switching to Completed.
- The acceptance stores seven distinct monitor captures through Completed and rejects blank, dark recovery-TTY, identical, or incorrectly sized output. It requires `aqua_installer_transaction_executed=false`; transaction execution and autostart remain disabled.

## Language And Keyboard Forms

- `InstallerFormState` owns bounded selection indices for the language and keyboard catalogs and synchronizes them from validated installer model values.
- Up, Down, Home, End, and Activate operate only on the catalog for the current Language or Keyboard step. Activate applies the catalog value through the existing model validation rather than writing arbitrary text.
- The initial catalogs provide Turkish, English, and German locale choices plus Turkish Q, Turkish F, and US keyboard layouts. Each stored value remains compatible with the existing installation metadata contract.
- `aqua-renderer` now draws real Language and Keyboard content screens with selected-row focus, applied-value status, labels, and details. Their probes require valid shared geometry and produce distinct deterministic checksums without requiring the Welcome logo layer.
- `scripts/check-installer-render.sh` regenerates and validates `build/installer-welcome.png`, `build/installer-language.png`, and `build/installer-keyboard.png` as 1280x800 RGBA PNG outputs.

## Disk Selection Form

- `InstallerFormState` consumes the bounded `StorageInventory` and retains both eligible and blocked disks for transparent presentation. Its initial selection is the first eligible target; no target is fabricated when none is eligible.
- Up, Down, Home, and End navigate only eligible disks. Blocked running-root, read-only, and zero-capacity candidates remain visible but cannot receive selection.
- Navigation alone never changes `InstallerModel::target`. Activate reuses `StorageCandidate::into_erase_target()` and only then applies the validated identity, preserving exact-device confirmation and revalidation boundaries.
- The Partitions raster shows device, model, capacity, eligibility, applied-target state, the destructive whole-disk warning, and the canonical `AQUA_EFI` FAT32 512 MiB plus `AQUA_ROOT` ext4 remaining-space plan.
- `scripts/check-installer-render.sh` additionally validates `build/installer-partitions.png` as deterministic 1280x800 renderer output.

## Time Zone Form

- The initial bounded catalog provides `Europe/Istanbul`, `UTC`, `Europe/Berlin`, and `America/New_York` as standard IANA identifiers. The list can grow without introducing free-form values into installer state.
- Up, Down, Home, End, and Activate reuse the tested choice-form controller. Selection is applied through `InstallerModel::set_timezone()` and restored from model state when navigating back.
- The Time Zone raster presents localized city and region labels, keyboard focus, and the applied-value marker using the same deterministic row contract as Language and Keyboard.
- `scripts/check-installer-render.sh` validates `build/installer-timezone.png` as the fifth deterministic 1280x800 installer screen.

## User Information Form

- The user form owns bounded username and display-name text plus an active-field index. Username input accepts only lowercase ASCII letters, digits, and underscore up to 32 bytes; display names reject controls and are bounded to 128 bytes.
- Password character and Backspace events are explicitly ignored by this state object. It receives only a `password_configured` boolean from the future secure input component, so password contents and lengths cannot enter `InstallerFormState`, `InstallerModel`, render probes, or install metadata.
- Activate constructs the existing validated `UserProfile`; empty or invalid names and an unconfigured password fail closed before the model can advance.
- The User Information raster draws username, display name, and password-status rows with active-field focus and applied-profile state. It never draws password contents.
- `scripts/check-installer-render.sh` validates `build/installer-user.png` as the sixth deterministic 1280x800 installer screen.

## Summary Form

- The Summary raster presents the validated disk identity and capacity, locale and keyboard, timezone, user, partition layout, and install mode without rebuilding those values from display-only state.
- Dry-run can proceed without a destructive phrase. Real mode accepts only the model-generated `ERASE /dev/...` phrase bound to the current target; changing target or mode invalidates the prior confirmation.
- The form bounds confirmation input to 160 bytes, rejects controls, and reports readiness only after model confirmation succeeds. The renderer shows a separate destructive warning surface and a confirmed indicator.
- `scripts/check-installer-render.sh` validates `build/installer-summary.png` as the seventh deterministic 1280x800 installer screen. The Buildroot readiness probe exports `target-bound-summary-confirmation-ready` without enabling live rendering or disk writes.

## Safety Boundary

- Dry-run and real installation use the same validated selections.
- Disk identity includes the device path, stable identity, model, and capacity.
- Real installation requires an exact `ERASE /dev/...` phrase bound to the currently selected target.
- Changing the target or install mode invalidates prior confirmation.
- The state model stores only whether a password was configured, never password contents.
- Real-target execution is hard-bound to a disposable QEMU `/dev/vdb` and requires the execution gate plus a second exact transaction opt-in. Other targets fail closed.

## Storage Probe

The state crate now includes a read-only Linux storage probe. It reads bounded metadata from `/sys/class/block`, `/proc/self/mountinfo`, and `/proc/cmdline`.

- At most 64 sysfs block entries are accepted per probe.
- Metadata reads are bounded and invalid UTF-8 or malformed numeric fields fail closed.
- Partitions and loop, RAM, zram, floppy, and optical pseudo targets are excluded from install candidates.
- Read-only and zero-capacity disks remain visible but cannot become an `InstallTarget`.
- The root device is resolved from mountinfo and the kernel `root=` argument. When root is a partition, its parent whole disk is blocked.
- Candidate order is deterministic and an eligible candidate must pass `into_erase_target()` before entering installer state.
- The probe only inventories kernel metadata. The later executor must revalidate device identity immediately before every destructive operation.

## Installer Prerequisites

- The Buildroot image provides `/sbin/sfdisk`, `/sbin/mkfs.fat`, `/sbin/mkfs.ext4`, `/bin/tar`, `/bin/mount`, and `/bin/umount`.
- The post-image hook rejects an image if any required path is missing or not executable.
- `validate_install_prerequisites()` resolves metadata through symlinks and accepts only executable regular files at bounded absolute paths.
- `revalidate_install_target()` repeats the bounded storage probe and requires the exact device path, stable identity, model, and capacity immediately before destructive work. A disappeared, changed, read-only, running-root, or otherwise blocked target fails closed.
- These checks establish prerequisites only. Execution additionally requires every QEMU gate and transaction opt-in condition below.

## Command Rehearsal

- `compile_install_commands()` accepts only the canonical 13-operation plan and the validated tool set.
- The compiler verifies target identity, GPT geometry, partition paths, filesystem labels, mountpoints, boot destinations, and operation order again.
- Partition creation becomes one bounded `sfdisk` argv specification with a bounded stdin recipe. FAT/ext4 formatting, root/EFI mounts, GNU tar extraction, and ordered EFI/root unmounts become seven additional specifications.
- Every command stores an absolute validated program path and a bounded argument vector. No shell command string is generated.
- Target revalidation, kernel copying, bootloader/config installation, and system configuration remain explicit deferred Rust operations rather than hidden command gaps.
- `NonExecutingInstallCommandRunner` only records the eight specifications. Its result is always `executed=false`; the separately gated probe executor is not used by rehearsal paths.

## Internal Operation Rehearsal

- `compile_internal_install_actions()` produces 11 bounded Rust-owned actions at three explicit anchors: before mounting root, before mounting EFI, and after mounting EFI.
- Directory preparation is recursive but every destination must remain component-confined below `/mnt/aqua-target`.
- Kernel and `BOOTX64.EFI` copies use sibling temporary paths and require an atomic rename contract. Generated GRUB and system configuration files use the same atomic-write contract.
- The GRUB content is generated from the validated root label, kernel path, and command line rather than copied from unchecked input.
- Locale, keyboard, timezone, and first-user metadata are bounded. The user file records only `password_configured=true`; no password or password hash enters the plan.
- `NonExecutingInternalInstallRunner` records the 11 actions without touching the filesystem and always reports `executed=false`.

## Transaction Rehearsal

- `build_install_transaction_graph()` requires matching source fingerprints and combines target revalidation, eight external commands, and 11 internal actions into one canonical 20-step graph.
- Root mountpoint preparation occurs before the root mount; EFI mountpoint preparation occurs after rootfs extraction; boot and system files are staged only after the EFI mount succeeds.
- Failure cleanup is separate from normal unmount steps and guarded by observed rehearsal state.
- A failure before root mount schedules no cleanup. A failure after root mount schedules root unmount. A failure after EFI mount schedules EFI then root unmount in reverse dependency order.
- Normal rehearsal consumes both normal unmount steps and produces no redundant cleanup.
- Fingerprint mismatches, changed command order, changed anchor counts, and invalid injected failure positions fail closed. The transaction runner still performs no target probe, command, or filesystem operation and reports `executed=false`.

## Temporary Filesystem Fixture

- `FixtureInstallRoot` accepts only an existing empty real directory below the canonical system temporary directory. `/`, `/mnt/aqua-target`, non-directories, symlink roots, non-empty roots, and locations outside the temporary tree are rejected.
- `FixtureInternalInstallExecutor` remaps canonical `/mnt/aqua-target` destinations into that fixture and executes only the 11 Rust internal actions. It cannot dispatch transaction command steps.
- Every existing path component is checked with symlink metadata before directory creation or file staging. Symlink components and symlink artifact sources fail closed.
- Artifact copies are limited to 16 MiB in this fixture path. Atomic files use a sibling `create_new` temporary file, explicit mode, `sync_all`, and rename; failed staging removes its temporary file.
- Tests compare installed kernel and EFI bytes and verify generated GRUB, locale, keyboard, timezone, and password-free first-user files.
- The report distinguishes `fixture_filesystem_executed=true` from `disk_commands_executed=false` so fixture success cannot be presented as a disk installation.

## Temporary Tool-Shim Fixture

- `FixtureToolShimRoot` grants process capability only to executable regular files below a real directory in the system temporary tree. Programs outside that root and symlink path components are rejected immediately.
- `FixtureToolShimRunner` walks the transaction graph but executes only command nodes. Target revalidation and internal filesystem actions remain outside this runner.
- Programs receive the exact bounded argv vector directly, never a shell command string. The environment is cleared, stdout/stderr are disabled, and only a temporary log directory variable is supplied.
- Bounded stdin is delivered through a pipe. Tests verify the complete `sfdisk` GPT recipe and both mount invocations as observed by the shims.
- Each shim has a two-second deadline. A timeout triggers kill and reap and is reported separately from a normal non-zero exit.
- Non-zero exit and timeout stop at the exact transaction step and reuse graph state to report conditional cleanup. A tar failure after root mount reports root cleanup; no cleanup command is executed by the fixture runner.
- Reports distinguish `shim_processes_executed=true` from `real_disk_tools_executed=false`. Buildroot's real `/sbin` and `/bin` tools cannot satisfy this temporary-root capability.

## Dry-Run Plan

- The target must be at least 2 GiB.
- The proposed disk layout is GPT with a 512 MiB `AQUA_EFI` EFI System Partition and an `AQUA_ROOT` ext4 root partition using the remaining space. Matching GPT partition names provide stable `PARTLABEL` boot identity without an initramfs.
- Virtio/SATA-style and digit-terminated NVMe/MMC partition paths are generated correctly.
- The plan records exact target identity, partition paths, labels, mountpoints, rootfs archive, kernel source/destination, locale, keyboard, timezone, and password-free account metadata.
- Every ordered operation is structured data. The plan is not a shell script and no operation is dispatched.
- Rendering always reports `plan_mode=dry-run`, `execution_allowed=false`, and `executed=false`.
- A deterministic fingerprint changes when any meaningful plan input changes.
- Artifact paths must be absolute, bounded, free of control characters, and contain no parent traversal.
- The selected strategy is GRUB2 x86_64 UEFI. Buildroot produces `efi-part/EFI/BOOT/bootx64.efi`; the plan installs it as the standard removable-media fallback `EFI/BOOT/BOOTX64.EFI` and writes `EFI/BOOT/grub.cfg` targeting `root=PARTLABEL=AQUA_ROOT`.
- The bootloader decision is recorded in [ADR 0002](adr-0002-bootloader.md). BIOS installation is outside the first v1 installer path.
- A complete plan has zero unresolved plan blockers, but remains non-executable by contract.

## QEMU Execution Gate

- `aqua-installer-probe execution-gate` is available only when DMI identifies QEMU, the kernel command line contains `aqua.installer_execution_gate=1`, and `AQUA_INSTALLER_QEMU_EXECUTION_ENABLE` exactly equals `QEMU_DISPOSABLE_TARGET_ONLY`.
- Exactly one eligible storage target must exist. Its path, stable identity, model, capacity, and eligibility are checked again through a fresh storage probe.
- Rootfs, kernel, and EFI bootloader artifacts must be non-empty regular files and cannot be symlinks. A bounded manifest must contain exactly their three expected filenames and matching SHA-256 digests.
- The host staging script creates a separate ext4 image from the actual Buildroot outputs. QEMU attaches it as read-only `/dev/vdc`, so it remains visible but blocked by the storage probe while writable `/dev/vdb` is the only target.
- Real installer state requires the exact target-bound `ERASE /dev/...` phrase. A mismatch fails before authorization.
- Successful authorization compiles the fingerprint-bound 20-step transaction and advances installer state to Installation, but does not invoke a transaction runner. It reports `transaction_execution_started=false`, disk writes remain absent, and QEMU verifies the target image hash is unchanged.

## Disposable QEMU Transaction

- `aqua-installer-probe execution-run` repeats the full execution authorization and additionally requires `AQUA_INSTALLER_QEMU_TRANSACTION_EXECUTE=ERASE_DISPOSABLE_VDB_NOW`.
- The executor refuses every target except `/dev/vdb`, dispatches absolute validated programs without a shell, clears the child environment, supplies only a bounded safe `PATH`, enforces a 180-second command deadline, and revalidates target identity at transaction checkpoints.
- The canonical sector-based GPT recipe creates a 512 MiB EFI System Partition and the remaining ext4 root partition. FAT/VFAT support is built into the Aqua kernel so the EFI partition can be mounted during installation.
- The 20-step graph formats and mounts both filesystems, extracts the real Buildroot `rootfs.tar`, atomically installs the kernel and EFI loader, writes GRUB and bounded password-free system metadata, then unmounts in dependency order.
- `InstallProgressEvent` maps the next real transaction step to stable preparing, partitioning, formatting, system, bootloader, configuration, and finalization phases. Percentages are derived only from completed graph steps, remain below 100 while running or failed, and reach 100 only after both the transaction and installer state complete.
- The packaged executor emits `[AQUA-INSTALLER-PROGRESS]` records with state, phase, operation, completed/total steps, and percent. QEMU acceptance requires the real success path to report `completed=20 total=20 percent=100` and the injected EFI-mount failure to stop at `completed=8 total=20 percent=40`.
- On command or internal-action failure, cleanup is derived from observed mount state and attempts EFI then root unmount. A QEMU-only `AFTER_EFI_MOUNT` injection proves both ordered cleanup commands complete, both mountpoints disappear from `/proc/mounts`, and both filesystems remain readable afterward.
- The host creates a fresh 4 GiB qcow2 target for every test. Before/after SHA-256 proves the target changed and the read-only artifact disk did not.
- A second QEMU process boots the installed ext4 root as `/dev/vda2` with the external development kernel and reaches the recovery marker.
- A third process starts with EDK2 pflash and no external kernel. Firmware discovers `EFI/BOOT/BOOTX64.EFI`, GRUB loads the installed kernel, `root=PARTLABEL=AQUA_ROOT` resolves the installed root without initramfs, `/sys/firmware/efi` is present, and recovery becomes ready.
